## 1.5 P0 confirmed by source: profile undo journal has no durable commit point

**Plan correction:** the initial protocol sketch in this section is superseded
by the Asa decision in §6.1. Implement the schema-2 prepared/committed boundary
there: committed durability linearizes the operation, in-memory publication
and settlement follow it, and cleanup failure does not turn a committed result
into an API error. Keep schema-1 as prepared/rollback on startup.

The new crash-atomic profile journal fixes process death during file writes, but
its final commit protocol is still not linearizable.

Current success path in:

~~~text
toad/internal/control/config_api.go
    setProfileRolesPolicyLocked
~~~

is:

~~~text
write undo journal
commit role TOMLs / profiles.list
apply memory
persist desired.json
bump revision
unlock m.mu

RemoveProfileCompositionUndo(stateDir)

if removal fails:
    return ERROR with the new profileSettlement
~~~

The wrappers:

~~~text
SetProfileRoles
CreateProfile
SetTunnelProfiles
~~~

call `settlement.schedule(m)` even when the returned error is non-nil.

Therefore:

~~~text
all new files + desired state are already live
API returns failure because undo-journal removal failed
new process start/stop settlement can still run
surviving journal means "rollback" at next startup
restart restores the OLD composition
~~~

The same command is thus observed as new state while running and old state after
restart.

The current journal invariant:

~~~text
journal exists == transaction did not commit
~~~

is insufficient because durable removal itself can fail after the transaction
effects are complete.

### Required architecture — explicit durable commit phase

Version the journal:

~~~go
const ProfileCompositionUndoSchema = 2

type ProfileCompositionUndoPhase string

const (
    ProfileUndoPrepared  ProfileCompositionUndoPhase = "prepared"
    ProfileUndoCommitted ProfileCompositionUndoPhase = "committed"
)

type ProfileCompositionUndo struct {
    Schema int
    Phase  ProfileCompositionUndoPhase
    Files  []ProfileUndoFile
}
~~~

Compatibility:

~~~text
schema1 -> always treat as prepared/rollback
schema2 prepared -> rollback originals
schema2 committed -> DO NOT rollback; only durably remove journal
~~~

New transaction:

~~~text
1. durable schema2 phase=prepared undo journal
2. write config targets
3. apply/persist desired target
4. update live memory
5. DURABLY rewrite journal phase=committed   <-- linearization point
6. schedule settlement / report command success
7. best-effort durable journal cleanup
~~~

If step 5 fails:

~~~text
command has NOT committed
restore exact original config + desired + memory
return error
settlement MUST be empty
keep prepared journal if rollback/cleanup cannot be proven
~~~

If step 7 fails:

~~~text
command remains SUCCESS
live state remains new
startup sees phase=committed and only removes the stale journal
never rolls the transaction back
~~~

Do not use journal deletion itself as the commit point.

### Wrapper rule

Change all wrappers to schedule only a committed settlement:

~~~go
if err == nil {
    settlement.schedule(m)
}
~~~

Even with the new journal phase, a failed API call must never start/stop roles
according to the rejected composition.

Required tests:

~~~text
fail before committed-journal rewrite:
    API error
    old memory/disk/desired
    no settlement
    restart old state

committed-journal rewrite succeeds, journal removal fails:
    API success
    new memory/disk/desired
    settlement runs
    restart keeps new state and only cleans committed journal

schema1 leftover:
    rollback-compatible

schema2 prepared:
    rollback

schema2 committed:
    cleanup-only, no rollback

restart during committed-journal cleanup:
    idempotent new state
~~~

## 1.7 P0: Create/RemoveTunnel restart-only lifecycle is not safe in managed mode

**Plan correction:** the initial add-only zone-set and disconnected-only
removal sketches below are superseded by the Asa decisions in §6.2-§6.3. Use
exact role/zone/activation records for staged add and a resumable retirement
tombstone for removal. Do not implement marker set-union without role bindings
or delete TOML before ownership cleanup.

The documented product compromise is that CreateTunnel/RemoveTunnel take effect
after a core restart. That does not make the current lifecycle safe.

### Create/import gap — managed marker is not extended

`CreateTunnel` correctly writes `leshy_zone = role name`, but an already-managed
activation has a durable marker whose `ManagedZones` was captured when managed
mode was enabled.

Startup:

~~~text
NewManager loads the new tunnel TOML
LoadCommittedManagedState reads the old marker
applyManagedMarker authorizes only marker.ManagedZones
new role is NOT added to managedSelectedRoles
~~~

So after the documented restart the new/imported tunnel can exist in the UI but
managed selected-route intents for it are denied.

Required architecture: additive marker extension at startup, under the existing
`policyMu -> writer lock` order.

Add in `toad/internal/control/committed_state.go`:

~~~go
func (m *Manager) extendManagedMarkerForCurrentRoles(
    state committedManagedState,
) (committedManagedState, error)
~~~

Call after transition recovery + fresh committed-state load and before
`RestoreCommittedManagedState`.

Algorithm:

~~~text
validate current configured managed zone identities
currentZones = canonical zones of current loaded roles that can own selected traffic
missing = currentZones - marker.ManagedZones

if missing empty:
    no-op

otherwise:
    policyMu
    -> writer lock
    -> re-read marker + committed generation
    -> prove activation/generation unchanged
    -> for every newly-authorized role, reject a selected checkpoint fenced
       to another activation/generation/platform/role
    -> durable atomic marker = canonical union(old zones, current zones)
       with SAME activation ID and generation
    -> re-read/validate marker
    -> return updated immutable committedManagedState
~~~

This is add-only within one activation. Removed-role zones may remain inert
tombstones until the next explicit Managed->Local->Managed activation; without
a current role mapping they cannot resolve to a route owner.

Do not require `leshy_zone == role name` as a global configuration rule. The
field exists to name the Leshy zone. Instead fix rendering so a routing list
named by role is rendered with that role's configured stable zone:

~~~text
role/list key:   role name
generated Name: role.EffectiveEndpointPolicy().Zone
route_target:   <publicationDir>/<role>.dev
IPv6 setting:   keyed by role, not by generated zone string
~~~

Add an explicit validated `RoleZones map[role]zone` to `leshyRenderPolicy` and
replace the generic filename-as-zone assumption in the production renderer.
This simultaneously closes orphan-list validation and supports legitimate custom
zones without diverging Leshy from the core zone->role index.

### Remove gap — deleting a loaded role destroys cleanup authority too early

Current `Manager.RemoveTunnel` immediately deletes the TOML. QML enables the
remove action whenever `Core.safeToMutate`; it does not require the role to be
disconnected/clean.

Crash sequence:

~~~text
connected role owns publication/selected routes/checkpoint
RemoveTunnel deletes role.toml
core/process crashes before graceful Close releases the role
restart no longer loads the role
startup has no role/config authority to restore/retire its ownership evidence
~~~

That can leave same-boot kernel selected routes or stale checkpoint/publication
evidence without a loaded owner.

Required safe restart-only removal:

~~~text
1. role may not be current non-direct bypass owner
2. role must already be desired=false
3. fence the role as removalPending so ConnectRole/profile edits cannot re-enable it
4. stop any residual process and run releaseRoleResources to successful completion
5. prove selected registry empty + publication withdrawn + no cleanup error
6. durable RemoveTunnel(TOML)
7. keep the in-memory role tombstoned/removalPending until restart
~~~

Do not silently auto-switch default route to direct as part of removal.

Implement the fence on the role struct, e.g. `removalPending bool`, and make
`ConnectRole`, profile composition changes and SetBypassMode reject a pending
removal. The long stop/release work runs without holding `policyMu`; the
removalPending fence prevents re-enable during that window.

Tests:

~~~text
CreateTunnel while managed + restart:
    marker extends with same activation/generation
    new role becomes managedSelected
    routing list/default owner works after normal readiness

custom configured zone:
    generated Leshy zone uses configured zone
    route target still points at role publication
    selected zone resolves to the role

RemoveTunnel connected role:
    rejected until disconnected

RemoveTunnel current bypass owner:
    rejected until default moved/direct

disabled clean role removal:
    resources proven absent
    TOML durably removed
    re-enable rejected before restart

crash after TOML removal:
    no selected/publication ownership remains to orphan
~~~

Native installed follow-up (G2/H2/U8e/U9e): create/import -> restart -> route;
disconnect -> remove -> restart -> role absent, sibling VPN remains healthy.

## 2.3 Required architecture — prepare the complete target handover before parking A

Do not add separate ad-hoc family/capacity checks to SetBypassMode. Add one
read-only preparation step owned by SelectedRouteManager:

~~~go
type BypassTargetPlan struct {
    Owner       string
    Runtime     core.RoleRuntime
    Generation  uint64
    Intents     []BypassHandoverIntent
}

func (m *SelectedRouteManager) PrepareBypassTarget(
    owner string,
    intents []BypassHandoverIntent,
) (BypassTargetPlan, error)
~~~

Exact checks:

~~~text
owner != ""
managedRoleCheck(owner) == true
roleRuntime(owner) exists
runtime.Desired == true
runtime.Validation.Healthy == true
runtime.Toad.IfIndex > 0

for every intent:
    IPv4 prefix -> runtime.Validation.Families.IPv4.Ready
    IPv6 prefix -> runtime.Validation.Families.IPv6.Ready

capacity:
    count current target DNS prefixes
    count only transferred DNS prefixes that are not already represented by
    the same target (role,prefix) physical ownership
    require final unique DNS count <= capacity
~~~

No kernel/registry mutation is allowed in PrepareBypassTarget.

Change SetBypassMode A -> B order to:

~~~text
policyMu
arm bypassTransition
SnapshotBypassIntents(A)
PrepareBypassTarget(B, intents)      # NEW, before first destructive mutation
ParkAndWithdrawBypass(A)
write/regenerate/reload policy B
ApplyBypassToOwner(B, preparedPlan)
CommitBypassHandover(A)
clear transition/quarantine
~~~

If PrepareBypassTarget fails:

~~~text
old selected routes unchanged
no parks created
bypass.conf unchanged
running Leshy policy unchanged
transition fence cleared
command returns the readiness/capacity reason
~~~

`ApplyBypassToOwner` must defensively re-read target runtime under the target
applyMu before each mutation. If readiness changed after preparation, it does
NOT silently ignore the preflight: return an error, keep A's verified parks,
keep bypassTransition/policy quarantine armed, and let the existing restart /
recovery path complete once B is Ready again.

This is the correct race semantics: preflight avoids predictable disruption;
parks still provide fail-closed protection if runtime changes after preflight.

Permanent tests:

~~~text

    SetBypassMode fails BEFORE ParkAndWithdraw
    A selected row remains Active/exact
    bypass.conf remains A
    zero target mutation

IPv4 equivalent

target Validation.Healthy=false / Desired=false / IfIndex=0:
    same pre-destructive refusal

target DNS capacity exhausted:
    same pre-destructive refusal

target readiness changes after prepare:
    A park remains Active
    authority quarantined
    restart/recovery can later converge
~~~

Native dual-profile harness must add one row that tries to move a tracked IPv6
catch-all prefix to a role whose IPv6 family is not Ready and proves the old
owner route remains selected; no physical-default fallback and no policy commit.

## 2.3a P0 confirmed: protected owner -> direct handover is broken for any resolved bypass prefix

A focused audit-only test on the current source proved a separate runtime bug in
the protected handover state machine:

~~~text
SetBypassMode("one")
Ensure(bypass, 203.0.113.96/32) -> Active on one
SetBypassMode("direct")
-> ERROR:
   apply the transferred prefixes to role "": the bypass handover needs an explicit owner
~~~

The temporary audit test was removed after reproduction.

Cause:

~~~text
toad/internal/control/config_api.go
    SetBypassMode

newOwner = "" for direct
handover == true when oldOwner owns managed bypass rows

after ParkAndWithdrawBypass(oldOwner) + policy commit/reload:
    SnapshotBypassIntents(oldOwner)
    ApplyBypassToOwner(ctx, newOwner, intents)   # newOwner == ""
~~~

SelectedRouteManager.ApplyBypassToOwner correctly rejects an empty owner, so
the command fails after the durable policy has already become direct, while
the old rows have been replaced by parks and the transition stays incomplete.

This is not merely an error-reporting defect: direct is the explicit product
escape from a VPN default route and must be a first-class protected handover
target.

Required fix:

~~~text
Do not keep a second runtime handover algorithm in SetBypassMode.

After ParkAndWithdrawBypass(source):
    mark source in bypassRecoveryOwners BEFORE any later fallible step

If bypass.conf write fails before target commit:
    cached/durable owner is still source
    call resumeBypassHandover(source)
    -> target==source branch restores/proves source rows and retires parks
    -> if restoration fails, keep pending/quarantine/fence

After target policy commit/reload:
    call resumeBypassHandover(source)

resumeBypassHandover already has the required three-way target semantics:
    target == direct   -> FlushBypassOwner(source), safely retire parks/records
    target == source   -> restore source under parks, prove, retire parks
    target == another  -> transfer to target, prove, retire source evidence
~~~

This also makes the earlier WriteBypassMode-failure hole explicit: once the
old route has been parked/withdrawn, simply clearing bypassTransition and
returning is invalid even though the durable policy itself did not change.

Permanent tests:

~~~text

    bypass.conf == direct
    zero source bypass selected rows
    zero source parks/checkpoint bypass records
    no ApplyBypassToOwner("") attempt
    transition/fence/quarantine cleared

A -> direct with FlushBypassOwner failure:
    durable policy may be direct
    source stays in bypassRecoveryOwners
    parks remain Active
    transition/quarantine remain armed
    retry/restart resume converges

A -> B, injected WriteBypassMode failure after ParkAndWithdraw:
    durable policy remains A
    immediate resume takes target==source branch
    A rows restored/proven
    parks retired

~~~

The native dual-profile acceptance should include an owner->direct row with an
already-resolved catch-all prefix, not only A->B transfers.

## 2.3b P0 source-confirmed: ParkAndWithdrawBypass error is not mutation-atomic

The pending-handover marker must be established before the first park mutation,
not merely after ParkAndWithdrawBypass returns success.

Current structure:

~~~text
ParkAndWithdrawBypass(owner):
    parkBypassRecords(owner)
        park entries one by one
        write checkpoint
    withdrawBypassRows(owner)
        remove selected rows one by one
        write checkpoint

SetBypassMode:
    if ParkAndWithdrawBypass(...) returns error:
        clear bypassTransition
        return
~~~

Both inner phases can fail after earlier entries were already mutated. In
particular, withdraw can remove one or more selected rows before a later
remove/checkpoint fails. The caller then clears the only zone fence even though
the source handover is partially materialized.

Required architecture refinement:

~~~text
after target preflight + captured transfer set, BEFORE first park:
    mark sourceRole in bypassRecoveryOwners
    keep bypassTransition armed
    quarantine route authority as handover-pending

ParkAndWithdrawBypass may then mutate.

On any error from park/withdraw:
    call the same resumeBypassHandover(sourceRole) while durable owner is source
    target==source repairs/reproves the old rows and retires parks
    clear pending/fence only after exact proof

If repair itself fails:
    return the joined primary+repair error
    keep bypassRecoveryOwners + quarantine + fence
~~~

Permanent fault-injection coverage must fail:
    an intermediate park write,
    an intermediate selected-row removal,
    the park checkpoint write,
    the post-withdraw checkpoint write,

## 2.10 P0 source-confirmed: role desired-state mutators are not serialized with policyMu

# 6. 2026-11-18 R8A source follow-up

## 6.1 Profile composition journal: observed mismatch

`SetProfileRoles` and `CreateProfile` route through
`setProfileRolesPolicyLocked` (`config_api.go:195-216,233-450`). The helper
captures TOML/registry/desired-state originals in the profile undo journal,
commits the source files, publishes in-memory composition and desired state,
then removes the journal. Startup recovery runs under the state lock before
Manager construction (`main.go:352-364`). The current schema-1 journal has no
commit marker; recovery treats every remaining journal as rollback and restores
the originals (`profile_undo.go:13-40,50-66,89-123`). The API wrappers schedule
the returned settlement even when the helper returns an error.

There is therefore no durable distinction between an uncommitted operation
that must roll back and an operation whose new files/state were published but
whose journal cleanup failed. The running process can report an error and
schedule settlement for the new composition, while a restart sees the
remaining schema-1 journal and restores the old files. Active
`SetTunnelProfiles` is a separate gap: its wrapper serializes with `policyMu`,
but active membership changes update runtime composition and desired state
without the same durable composition journal; the inactive/disk-only case
rewrites one role TOML (`config_api.go:82-179`).

### Asa decision: one durable profile-composition boundary

Use one Manager transaction helper for `CreateProfile`, `SetProfileRoles` and
`SetTunnelProfiles`. Under `policyMu`, build and validate the full plan before
mutation. The plan covers touched TOMLs, profile registry and `desired.json`
when desired state changes.

The executor protocol is:

~~~text
write and durably confirm schema-2 prepared journal with exact original bytes,
permissions and absent-file markers
apply all planned files and durably confirm them; keep the old in-memory
snapshot and epoch
atomically replace the journal with committed and durably confirm it
publish the complete new composition, desired flags and epoch under m.mu
return success and schedule settlement only after publication
remove committed journal as retryable cleanup; cleanup failure does not undo
the committed API outcome or settlement
~~~

The durable `committed` marker is the linearization point. If writing it
returns an error, resolve the durable outcome: confirmed `prepared` rolls back
the exact old image and returns error without settlement; confirmed `committed`
is completed as a commit; unresolved outcome keeps composition quarantined,
publishes neither snapshot and forbids writes to affected sources. An
unproven rollback or prepared-journal removal has the same write prohibition.
Startup treats schema 1 as prepared and rolls it back; schema-2 prepared also
rolls back, committed loads the new sources then cleans up, and unknown or
corrupt journal state stops startup. A durable atomic replacement alone is
enough only when exactly one file changes and neither active composition nor
desired state changes. A role being unloaded does not establish that
condition.

Executor crash matrix: after prepared; between TOML/registry/desired writes;
after the last file but before committed; after committed but before in-memory
publication; cleanup failure and restart; injected committed-write outcomes
for prepared/committed/unresolved; schema-1 recovery; rollback failure;
active SetTunnelProfiles; and a true one-file inactive move. For each case,
compare exact files, API outcome, runtime snapshot and settlement scheduling.

### Asa decision: prepared add and tombstoned retirement

means “saved; restart required”. Until startup applies that record, the role

the recorded identity, extend `ManagedZones` within the existing activation,
construct the managed role map and verify generated configuration before

mismatch stop application with explicit diagnostics.

~~~text

durably write a retiring tombstone; close admission and invalidate older
~~~

## 6.3 Routing-list/render identity: source confirmation and pending Asa decision

Two other R8A residuals remain present in the synced product source:

- `Manager.SetRoutingList` still writes the list directly and only bumps the
  snapshot revision (`config_api.go:1288-1303`); it does not regenerate or

  `SetRoutingListLive`.
- Standalone `generateLeshy` still calls permissive `ReadBypassMode` before
  rendering (`cmd/kikimora-core/generate.go:53-64`). That helper maps every
  read error to `direct`, while `ReadBypassModeStrict` preserves missing/empty
  as direct but returns errors for unreadable or invalid persisted policy
  (`config/bypass.go:32-62`). Make generation use the strict reader and return
  its error; retain missing/empty as valid direct policy.

The current `SetRoutingListLive` checks only that the reserved `bypass` name
is not used as a role list, then writes the requested filename, regenerates
Leshy configuration and reloads the service (`config_api.go:1313-1361`). It
does not establish that the name belongs to a loaded role before mutation.
`ListRoutingFiles` enumerates every valid `*.txt` file in the routing
directory (`config/routing_lists.go:17-37`), and `BuildLeshyZones` renders
each filename as the zone name and `<filename>.dev` target (`:42-73`). A stale
`ghost.txt` therefore remains eligible for generation even when no `ghost`
role is loaded. This is also the current R8A blocker in `docs/roadmap.md:84-94`.

The renderer and route authority use different identities today:

- `BuildLeshyZones` takes the role-list filename as generated zone name.
- `Manager.newSelectedRouteManager` builds its zone-to-role index from each
  loaded role's `EffectiveEndpointPolicy().Zone`
  (`selected_routes.go:827-856`).
- `validateManagedRouteIdentityLocked` separately requires nonempty unique
  effective zones for a candidate managed default owner
  (`config_api.go:1005-1027`).

Inference from those source paths: a valid custom zone whose name differs from
the role/list key can be rendered under one zone identity while selected-route
authorization indexes another. In managed mode, the zone-less default-owner
guard is also still conditional on `managedSelectedRoles[role]` or
`managedSelectedRoles[activeProfile]` (`config_api.go:991-1001`). Because the
zone-less role is absent from that set and `activeProfile` names a profile,
not a role, the guard can skip the identity check. This matches the R8A plan's
focused regression requirement; the historical reproduction is recorded in
§1.3, while this continuation confirms the same guard remains in synced

### Asa decision: one validated role-to-zone authority

`RoleZones map[role]zone` is a required validated renderer input, sourced from
loaded role configurations' stable `EffectiveEndpointPolicy().Zone`. The route
resolver must use the inverse of this exact same pair. Example: `office.txt`
for role `office` with zone `vpn-office` renders `Name=vpn-office`, targets
`office.dev`, and an intent for `vpn-office` resolves back to `office`. The
synthetic `bypass` zone remains reserved.

Validate the full mapping before applying it, including roles without a
routing-list file. In managed mode any role assigned routing must have a
nonempty unique zone and confirmed enrollment for that pair. A loaded role
without a valid routing identity cannot own a list or become VPN default
owner. Check every managed default-owner assignment directly; do not gate the
check on prior membership in `managedSelectedRoles`.

`SetRoutingListLive` validates the role key and admission under `policyMu`
before file mutation. Startup, activation, marker restore, regeneration and
standalone generation use the same policy contract. Unknown, unenrolled or
zoneless owners fail before writing generated config or reloading Leshy. The
renderer does not derive identity from a filename. Any retained local-only
fallback must be explicitly resolved by the role-map builder before render.

Lifecycle integration: a pending add reserves its name/zone but is excluded
from the running renderer and resolver until confirmed startup enrollment. A
retiring tombstone retains the old pair for cleanup and excludes it from new
admission; teardown also removes the role's policy inputs from the active set.
Name and zone reuse is allowed after teardown and marker update are confirmed.

### Legacy activation identity remains a gate

Neither supported marker format records role-to-zone bindings: schema 2 stores
only the `ManagedZones` set alongside activation metadata
(`selected_routes.go:986-995`), while schema 1 stores that same set with socket
and core version and is parsed only by upgrade detection (`:997-1006`). A
selected-route checkpoint stores both `Role` and `Zone`
(`routing/selected_registry.go:218-231`), but only for roles with checkpointed
routes. A role with no route records has no such pair evidence. Consequently,
the old marker cannot detect two custom zones swapped between roles when the
set of zone names stays unchanged.

### Asa decision: fail closed on incomplete legacy pair evidence

Do not auto-fill a schema-1 or schema-2 marker with role-to-zone pairs unless
every pair is independently proven to belong to that activation and agrees
with the current TOML. Current unique TOML zones, equality with the
`ManagedZones` set, and absence of a role checkpoint are not proof.

Under the state lock, finish recovery of any legacy transition first. For each
zone in the restored marker, find independent durable evidence of the exact
role/zone pair for this activation and compare it to current configuration.
A checkpoint is usable only if its activation ownership is itself proven; a
synthetic `bypass` record does not prove a stable role zone. Any conflict,
stale evidence or missing pair blocks route authority.

When evidence is complete, durably persist the verified pair map before
opening admission, retaining the activation identity and role resources.
Subsequent startup validates exact pairs from that marker, including custom
zone swaps that leave the zone-name set unchanged. When evidence is incomplete,
keep the old marker and checkpoints available, hold managed authority closed,
and report which zones lack a proven pair. The recovery route is explicit
reactivation with validated current TOMLs only after old-activation ownership
is proven complete and old admission is closed. A proven empty state permits a
clean new activation; it does not prove historical role/zone pairs. No
checkpoint alone does not prove the system is empty.

Acceptance for both legacy schemas: complete pair evidence with activation
preserved; missing pair for a role without routes; checkpoint from another
activation; `bypass` as the only evidence; conflicting evidence; custom-zone
swap; crash before/after binding persistence; explicit reactivation after
proven cleanup; and refusal while old ownership remains. Keep legacy-phase
recovery and role-to-zone proof as separate C8R gates; successfully parsing an
old marker does not permit Ready by itself.

Acceptance: custom-zone path `office.txt → Name=vpn-office → target=office.dev
→ Ensure(vpn-office) → office`; duplicate zone even without a `.txt`;
unknown setter without write/reload; stale orphan at startup and regeneration;
zoneless managed default owner; custom-zone swap between roles with the same
`ManagedZones` set; and crash between lifecycle record and marker update. After
recovery, renderer and route resolver must use the same confirmed pairs.
