Root-cause findings after the privileged run
--------------------------------------------
Two distinct issues were identified.

1. Stable transport restart hand-off

On canonical underlay change:
- Controller.SetUnderlay marks previously Ready roles Recovering and clears
  ValidatedEpoch.
- AWG advertises RestartTransportKeepingTUN.
- ordered recovery executes fail-closed preparation, endpoint rebind and
  RestartTransport.
- RestartTransport returns synchronously before the AWG peer is healthy.
- recovery immediately executes Validate.
- current validation is not yet eligible/healthy.
- Engine treats this expected transient condition as a fatal generic recovery
  error and exposes RoleFailed.
- retries restart from the full recovery sequence instead of waiting for the
  same Toad/transport to become healthy.

This violates the desired level-triggered recovery model: protocol transport
may need time to recover after a reset and transient validation failure is not
a terminal role failure.

2. RouteReady semantics regression introduced in 46c7aaa

Existing architecture explicitly defines:

  route_ready = managed interface is a valid fail-closed route target

and explicitly states that route_ready does NOT require remote peer health.

A stable TUN with healthy structure but unhealthy protocol is a valid degraded
state with route_ready=true; selected traffic can remain trapped in that TUN
without falling through to the physical default.

The 46c7aaa runtime change coupled AWG RouteReady to health. That coupling is
too strong and must be reverted.

AWG Backend.Validate remaining requirement
------------------------------------------
The separate AWG validation change remains correct:

- recent AWG handshake may validate Healthy
- no/stale handshake must not certify a current underlay epoch

The fix must keep validation health-aware while restoring RouteReady as a
structural TUN property.

Phase B assertion correction required
-------------------------------------
The current Phase B test requires both:
- route_ready=false
- parking.active=true

That is not the documented stable-TUN contract.

Correct acceptance must prove:
- AWG is not Ready/current-epoch validated while protocol is unhealthy
- recovery remains non-terminal
- selected AWG traffic is fail-closed
- if the TUN remains structurally valid, route_ready may remain true
- explicit parking is required only for owned selected routes that would
  otherwise lose their safe route target
- a selected route retained through the stable AWG TUN is itself a valid
  fail-closed result
- no physical-default fallback is permitted
