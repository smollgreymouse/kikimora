# 2. AUD1 — reopen PROD1: profile composition is not one durable transaction

## 2.1 Confirmed SetTunnelProfiles failure

A temporary audit test was created, run, and removed. It staged:

~~~text

active_profile = work
desired store = failingDesiredStateStore

~~~

The command correctly returned a desired-state persistence error, but the role
TOML had already changed:

~~~text
before disk membership: [default work]
after disk membership:  [default]
~~~

The desired flag rolled back while config membership did not.

## 2.2 Confirmed SetProfileRoles failure

A second temporary audit test was created, run, and removed:

~~~text
work = [one]
active_profile = work
desired store = failingDesiredStateStore

SetProfileRoles("work", ["two"])
~~~

It failed exactly as follows:

~~~text
one: [default work] -> [default]
two: [default]      -> [default work]
~~~

even though the API returned failure.

The tests were removed after reproduction; no audit-only Go source remains.

## 2.3 Root cause

Code points:

~~~text
toad/internal/control/config_api.go
    Manager.SetTunnelProfiles
    Manager.SetProfileRoles

toad/internal/control/control.go
    Manager.applyActiveProfileIntentLocked
    Manager.rollbackProfileIntentLocked
    Manager.scheduleProfileSettlement

toad/internal/config/create_profiles.go
    SetTunnelProfiles
    SetProfileMemberships
~~~

The previous PROD1 fixed latest-intent process settlement and mid-TOML
multi-role rollback. It did not make these resources one commit:

~~~text
role TOML memberships
in-memory role.cfg.Profiles / profileToRoles
desired.json active composition
profileSwitchEpoch / scheduled settlement
~~~

A failure in the third item can therefore leave the first two committed.

## 2.4 Mandatory architecture — one policy/composition transaction

Add to `Manager`:

~~~go
policyMu sync.Mutex
~~~

It serializes the *durable policy transaction only* for:

~~~text
SetActiveProfile
CreateProfile
SetProfileRoles
SetTunnelProfiles
SetBypassMode
SetRoutingList
SetRoleIPv6
managed-mode config transitions that rewrite generated Leshy config
~~~

Call this lock `policyMu`, not `compositionMu`: profile composition and live
Leshy policy share one generated-config/default-route invariant. The lock is
never held while waiting for a Toad process to start/stop.

A third temporary audit reproduction found another partial-commit path:

~~~text
CreateProfile("broken", ["missing"])
-> API returns error "unknown role"
-> profiles.list already contains "broken"
-> profileToRoles already exposes the empty "broken" profile
~~~

So the transaction must include the declared-profile registry as well as role
TOMLs.

Add one prepared profile transaction in:

~~~text
toad/internal/config/create_profiles.go
toad/internal/config/profiles_registry.go
~~~

Fixed API shape:

~~~go
type ProfileCompositionPlan struct {
    Memberships      []ProfileMembership
    DeclaredProfiles *[]string // nil = leave profiles.list untouched
}

type ProfileCompositionTxn struct {
    // private exact-byte snapshots, original modes and existed/not-existed bits
}

func PrepareProfileComposition(
    dir string,
    plan ProfileCompositionPlan,
) (*ProfileCompositionTxn, error)

func (tx *ProfileCompositionTxn) Commit() error
func (tx *ProfileCompositionTxn) Rollback() error
~~~

`CreateProfile` must validate every requested role **before** committing
`profiles.list`, then commit registry + memberships through this same
transaction. A failed CreateProfile must not leave an empty declared profile
unless the caller explicitly requested a valid empty profile.

`SetTunnelProfiles` uses the same transaction with one membership and a nil
DeclaredProfiles pointer. `SetProfileRoles` uses it with all changed
memberships. There must not be separate rollback implementations.

Requirements:

1. `Prepare` reads and validates every affected role file before mutation.
2. `Commit` uses the existing atomic-per-file replacement.
3. if any file write fails, all prior files are restored before return.
4. `Rollback` works after a successful `Commit`, specifically for a later
   `persistDesiredLocked` failure.
5. rollback preserves original file mode and exact original bytes.

Control transaction for both membership APIs:

~~~text
lock policyMu
validate profile/role/bypass invariant
PrepareProfileComposition
capture old in-memory membership/profile map
Commit TOMLs
apply new membership in memory
rebuildProfileMapLocked
applyActiveProfileIntentLocked -> persistDesiredLocked
    failure:
        rollback desired flags/epoch
        restore old in-memory memberships
        rebuildProfileMapLocked
        tx.Rollback()
        return errors.Join(original, rollback errors)
commit revision
unlock policyMu
scheduleProfileSettlement(epoch, changed, want)
~~~

`SetTunnelProfiles` must use this same multi-file transaction even though it
normally touches one role. There must not be two atomicity implementations.

`SetActiveProfile` takes `policyMu`, validates/commits desired state,
unlocks, then schedules settlement as today. `CreateProfile` takes the same
lock and must use an internal `setProfileRolesPolicyLocked` helper rather than
recursively calling the public locked method.

## 3.1 Reproduction

after the old bypass zone had been flushed but before the cached owner was
changed.

While blocked it issued:

~~~text

~~~

Current code accepted the intent under old owner `one`. After allowing the
switch to commit, the selected registry still contained an active `one`
record for that prefix.

The temporary test was removed after reproduction.

## 3.2 Root cause

Code:

~~~text
toad/internal/control/config_api.go
    Manager.SetBypassMode
    Manager.bypassOwnerLocked
    Manager.restoreBypassMode

toad/internal/control/selected_routes.go
    Manager.newSelectedRouteManager
    SelectedRouteManager.SetBypassOwner

toad/internal/control/api.go
    EnsureLeshyRoute / ForgetLeshyRoute / FlushLeshyZone
~~~

Current order:

~~~text

write bypass.conf
regenerate config
reload Leshy
update cached m.bypassMode = new
~~~

During the middle of that sequence, selected-route authorization still exposes
the old cached owner. The flush is therefore not a fence.

## 3.3 Mandatory architecture — fail-closed policy transition

Use the AUD1 `policyMu` to serialize bypass/profile/membership and live Leshy policy
commits.

Add under `m.mu`:

~~~go
type bypassTransition struct {
    Active bool
    From   string
    To     string
}

bypassTransition bypassTransition
~~~

Do not expose `From` as a routable owner while `Active`.

Change the selected-route resolver callback from:

~~~go
func() (string, bool)
~~~

to a typed decision, e.g.:

~~~go
type BypassOwnerDecision struct {
    Role       string
    Available  bool
    Transition bool
}

func() BypassOwnerDecision
~~~

or equivalent explicit API. Do not overload `Available=false` because
`direct` and `transition in progress` have different diagnostics.

`SetBypassMode` order is fixed:

~~~text
lock policyMu
validate new role against active profile
set bypassTransition{Active:true, From:old, To:new}
bump snapshot/authority diagnostic if needed

FlushZone("bypass") while resolver can still identify old owner ONLY for the
internal flush path; external Ensure is denied while transition active

write bypass.conf
regenerate Leshy config
reload Leshy
commit m.bypassMode=new
clear transition
bump snapshot
unlock policyMu
~~~

Internal flush must receive an explicit owner or transaction token; do not make
external requests temporarily routable to the old owner just so FlushZone can
find it. Preferred exact change:

~~~text
SelectedRouteManager.FlushBypassOwner(ctx, oldOwner)
~~~

which retires only `Zone=="bypass"` records belonging to that explicit role.

On write/regenerate/reload failure:

~~~text
restore bypass file/config + reload old policy
only after old policy is restored:
    m.bypassMode=old
    clear transition
return errors.Join(primary, rollback)
~~~

During `bypassTransition.Active`:

~~~text
EnsureLeshyRoute zone=bypass -> typed retryable API denial
Forget/Flush from external Leshy -> same transition fence unless they carry
                                   the internal transaction path
ordinary named role zones   -> unaffected
~~~

The Desktop already renders command errors; no optimistic bypass owner may be
committed before the core confirms success.

## 3.5 AUD2B — every live Leshy policy mutation must be transactional

The audit reproduced two more failures in existing user-facing settings:

~~~text
SetRoleIPv6("one", false):
    generated setting/config changes
    reloadHook call count = 0
    => running Leshy keeps the old IPv6 policy until some later restart

SetRoutingList("one", "example.org"):
    reloadHook returns "reload failed"
    API response is still OK
    message = "one list saved, but Leshy did not restart: reload failed"
~~~

The second path also leaves the new list on disk, so the API has reported
success from a half-applied policy. The first path can do the same on a
RegenerateLeshyConfig failure: `role-ipv6.json` has already changed.

Exact code points:

~~~text
toad/internal/control/api.go
    SetRoutingList branch

toad/internal/control/config_api.go
    Manager.SetRoutingList
    Manager.SetRoleIPv6
    Manager.SetBypassMode
    Manager.RegenerateLeshyConfig
    Manager.RegenerateLeshyConfigForMode

toad/internal/config/routing.go
    ReadRoutingList / WriteRoutingList

toad/internal/config/routing_lists.go
    ReadRoleIPv6Settings / WriteRoleIPv6Setting

toad/internal/control/mode_transaction.go
    EnableManagedLeshy
    DisableManagedLeshy
    RecoverManagedModeTransition
~~~

This is one architecture problem: several APIs rewrite inputs of one generated
Leshy config without one policy transaction.

### Mandatory policy lock

The `policyMu` introduced by AUD1 is the **single in-process writer lock** for
all live policy/config mutations:

~~~text
SetActiveProfile
CreateProfile
SetProfileRoles
SetTunnelProfiles
SetBypassMode
SetRoutingList
SetRoleIPv6
EnableManagedLeshy
DisableManagedLeshy
RecoverManagedModeTransition
~~~

The cross-process mode writer lock remains authoritative for mode transition
durability; lock order is fixed:

~~~text
policyMu
-> mode writer lock (when the operation is a mode transition)
-> m.mu only for short in-memory snapshots/commits
~~~

No path may acquire `policyMu` while already holding the mode writer lock.

Refactor generated-config writing so transaction callers do not recursively
lock:

~~~go
func (m *Manager) RegenerateLeshyConfig() error {
    m.policyMu.Lock()
    defer m.policyMu.Unlock()
    return m.regenerateLeshyConfigPolicyLocked()
}

func (m *Manager) regenerateLeshyConfigPolicyLocked() error
~~~

`RegenerateLeshyConfigForMode` gets the same private locked implementation;
Enable/Disable/Recover enter `policyMu` before their writer-lock transaction.

### SetRoutingList transaction

Move the whole command from the API switch into one manager method:

~~~go
func (m *Manager) SetRoutingListLive(ctx context.Context, name, content string) error
~~~

Fixed order under `policyMu`:

~~~text
validate name/content
snapshot exact old list bytes + existed/not-existed state
write new list atomically
regenerate generated Leshy config
reload Leshy
commit revision
return success
~~~

On regenerate or reload failure:

~~~text
restore old list exactly (remove it if it did not exist)
regenerate the old generated config
reload the old policy
return errors.Join(primary failure, rollback failure)
~~~

The API `SetRoutingList` branch must set `err` from this method. There is no
allowed "OK, but Leshy did not restart" result.

### SetRoleIPv6 transaction

Add:

~~~go
func (m *Manager) SetRoleIPv6Live(ctx context.Context, role string, enabled bool) error
~~~

or make the current `SetRoleIPv6` itself own this transaction.

Snapshot the exact previous `role-ipv6.json` bytes/existence. Then:

~~~text
write setting
regenerate config
reload Leshy
only after reload success bump revision and return OK
~~~

On either failure restore the exact JSON file/existence, regenerate old config
and reload old policy. A successful SetRoleIPv6 **must invoke reload exactly
once**.

Do not rollback by reserializing a map when exact bytes are available; preserve
unknown future fields/order by restoring the original bytes.

## 3.6 Generated config must be rendered from an explicit policy snapshot

The current `RegenerateLeshyConfigForMode` temporarily overwrites:

~~~text
m.managedSocket
m.managedActivationID
m.modeGeneration
~~~

then calls the ordinary generator and restores those fields in a defer. That was
safe only while generated-config writers were effectively serialized by
convention. With AUD2's real `policyMu`, keep this path explicit rather than
making temporary manager truth part of the rendering algorithm.

Refactor:

~~~go
type leshyRenderPolicy struct {
    Mode           ManagedLeshyMode
    Socket         string
    ActivationID   string
    ModeGeneration uint64
    BypassMode     string
    RoleIPv6       map[string]bool
    RoutingDir     string
    PublicationDir string
}

func (m *Manager) captureLeshyRenderPolicyLocked(...) (leshyRenderPolicy, error)
func (m *Manager) renderLeshyConfig(policy leshyRenderPolicy) ([]byte, error)
func (m *Manager) writeLeshyConfigPolicyLocked(policy leshyRenderPolicy) error
~~~

The renderer takes explicit values and never mutates `Manager` just to
calculate bytes. `EnableManagedLeshy`, `DisableManagedLeshy`, transition
recovery and ordinary list/bypass/IPv6 transactions all use the same renderer.

This also gives rollback a precise input: regenerate from the captured old
policy snapshot instead of re-reading a mixture of already-restored and
not-yet-restored files.

Update the stale contract in:

~~~text
toad/internal/config/leshy_reload.go
~~~

which currently says reload failure is "best effort" because files are already
on disk. After AUD2, user-facing live mutations are fail-closed transactions:
reload failure is command failure and source/generated files are rolled back.

# 4. AUD3 — PROD4 real DNS chain is currently bypassed after role leave/rejoin

## 4.1 What the PROD4 harness currently does

`linux/tests/toad/managed-dual-profile-netns.sh` has useful D1-D18 structure,
but D12/D13 do not currently prove the product path after a role leaves and
rejoins.

The recorded investigation already observed:

~~~text
DNS answer is returned
core selected_routes.ensures does not increase
restarting Leshy makes the same name route again
~~~

The harness then uses direct `routeprobe ensure` calls and allows the DNS path
to be only a NOTE. That is not acceptable for PROD4.

## 4.2 Root cause proven from pinned Leshy + core

Pinned Leshy:

~~~text
smollgreymouse/leshy@61786d4
src/routing/kikimora.rs
    subscription_pump
    snapshot_invalidations

src/routing/registry.rs
    RouteRegistry::ensure
~~~

Leshy invalidates a managed zone only when the core snapshot exposes a changed
`publication.generation` with a usable `publication.zone`.

Its registry fast-path is:

~~~text
Verified + same desired intent + same epoch
-> AlreadyMatching
-> no backend EnsureLeshyRoute RPC
~~~

Kikimora managed explicit release currently does:

~~~text
toad/internal/control/recovery_driver.go

releaseManagedSelected:
    FlushZone(...)
    UpdateRoleResources(..., leshy.PublicationState{}, ...)
~~~

and `Withdraw` similarly clears publication identity.

Therefore Leshy sees neither the old zone nor a changed generation on withdraw.
A later republish can carry the same generation. Its stale Verified entry never
gets dirtied, exactly explaining why a Leshy process restart fixes the route.

## 4.3 Mandatory core architecture — admission-fenced publication generations

Do not fix this by restarting Leshy on every profile switch, and do not merely
increment a counter after FlushZone.

An Ensure captures `routeGeneration` before it takes the role's `applyMu`.
Therefore a post-flush increment without an admission fence still allows a
concurrent old-generation Ensure to land after the drain.

Implement two explicit publication-lifecycle operations in:

~~~text
toad/internal/control/selected_routes.go
toad/internal/control/selected_transactions.go
~~~

Fixed API shape:

~~~go
// Explicit disconnect/profile departure. Leaves the role selected surface
// frozen until the publication is opened again.
func (m *SelectedRouteManager) RetirePublication(
    ctx context.Context,
    role string,
    zone string,
) (newGeneration uint64, err error)

// Successful republish. Reopens admission WITHOUT another generation bump.
func (m *SelectedRouteManager) OpenPublication(role string) uint64
~~~

`RetirePublication` order is mandatory:

~~~text
1. Freeze(ctx, role):
       set frozen=true before waiting
       wait for inFlight==0
       from this point no new Ensure can capture the old generation

2. under the role apply transaction:
       retire every registry record whose Zone == zone
       clear verification tokens
       increment routeGeneration exactly once
       write the empty/new-generation checkpoint

3. leave frozen=true
4. return new generation
~~~

Do not implement step 2 by calling the public `FlushZone` through a dynamic
zone resolver if an explicit role is already known. Add/use an internal
`flushRoleZoneLocked(ctx, role, zone)` helper so bypass/profile resolver state
cannot redirect the retirement.

`OpenPublication`:

~~~text
under m.mu:
    keep current routeGeneration
    keep restore/integrity fences
    set frozen=false only when no restorePending/integrity quarantine forbids it
    cond.Broadcast()
return current generation
~~~

It is idempotent for an already-open healthy role.

Then separate the two withdrawal cases in
`toad/internal/control/recovery_driver.go`.

### Explicit disconnect / profile departure: releaseManagedSelected

~~~text
generation, err := selectedRoutes.RetirePublication(ctx, role, zone)
if err != nil:
    keep selected admission frozen
    return error

UpdateRoleResources:
    Published:  false
    Zone:       zone
    Generation: generation
    Families:   current families
~~~

This is the generation change that invalidates Leshy's stale Verified key.

### Recovery Withdraw

Recovery already owns:

~~~text
FreezeSelected -> ... -> UnfreezeSelected
~~~

so `Withdraw` must **not** invent a second increment. After the publication
file is withdrawn, preserve identity:

~~~text
Published:  false
Zone:       zone
Generation: selectedRoutes.currentGeneration(role)
Families:   current families
~~~

Later `UnfreezeSelected` performs the existing one generation increment and,
because Zone survived Withdraw, its snapshot now carries the changed
`zone + generation` that pinned Leshy invalidates.

### Republish

In `recoveryDriver.Publish`:

~~~text
services.Leshy.Publish(...) succeeds first
if managed:
    generation := selectedRoutes.OpenPublication(role)
UpdateRoleResources:
    Published:true
    Zone:zone
    Interface:...
    Generation:generation
~~~

Opening after the publication file succeeds gives a small fail-closed window
(Ensure can be denied while frozen) rather than accepting routes for a
publication that failed to appear.

**Never publish `PublicationState{}` for a managed withdrawal.**

Pinned Leshy's current `snapshot_invalidations` is compatible with this
contract: it does not require `published=true`; it consumes zone + changed
generation.

Add Kikimora unit tests in:

~~~text
toad/internal/control/selected_routes_test.go
toad/internal/control/selected_transactions_test.go
toad/internal/control/recovery_driver_test.go
~~~

Required cases:

~~~text
RetirePublication:
    concurrent Ensure already in flight is drained before generation bump
    Ensure arriving after frozen=true is denied and cannot capture old generation
    zone records retire, unrelated role/zone survives
    verification cleared
    generation increments exactly once
    checkpoint records the new generation and no retired ownership
    remains frozen

Publish after explicit departure:
    failed Leshy Publish leaves selected admission frozen
    successful Publish calls OpenPublication and keeps same invalidation generation

managed recovery Withdraw:
    unpublished snapshot retains zone/current generation
    subsequent UnfreezeSelected increments once
    resulting snapshot is unpublished + same zone + N+1
~~~

Add a Leshy unit test at the pin/future companion branch to freeze the
cross-repo contract:

~~~text

-> unpublished same zone generation N+1
=> RouteInvalidation::Zone(zone)

republished generation N+1
=> no duplicate invalidation required
~~~

If the companion test requires a Leshy source commit, update
`.github/managed-routing-companion.env` only after its CI passes; never point
acceptance at moving master.

# 6. AUD5 — Desktop all-OS gate is red; resync algorithm drops a full snapshot

## 6.1 CI truth

~~~

Thus UIR5 golden evidence is valid, but UIR1/U7 all-OS Desktop acceptance is
reopened.

## 6.2 Root cause and protocol decision

Files:

~~~text
desktop/src/core/RealCoreClient.cpp
    processIncomingMessage
    handleSnapshot

desktop/tests/RealCoreClientTest.cpp
    IpcFixture
    resynchronizesAfterRevisionGap
    keepsUpdatingAfterAStaleResyncReply
~~~

The core subscription protocol sends **full snapshots**, not deltas:

~~~text
toad/internal/control/api.go
    serveConnection
    serveSubscription
~~~

Responses to ordinary requests and the subscription goroutine share one
connection and can interleave under `writeMu`.

Current client behavior while `m_resyncPending`:

~~~text
a newer streamed snapshot arrives
-> if requestId != resync, return without applying it
~~~

If that full snapshot arrives before a stale resync response, it is discarded.
The stale resync then clears `m_resyncPending`, leaving the client at the old
revision until another material push happens. Windows CI exposed exactly that
ordering.

Because every subscription frame is a complete snapshot, **a revision gap does
not make the newer frame unusable**.

## 6.3 Mandatory client algorithm

Keep a resync request as a consistency probe, but never block application of a
newer full snapshot.

In `RealCoreClient::handleSnapshot`:

~~~text
1. map diagnostics independently as today
2. if nextRevision == 0 -> ignore
3. if requestId == resync -> clear m_resyncPending
4. if nextRevision <= m_revision -> ignore as stale
5. if streamed && nextRevision > m_revision+1 && !m_resyncPending:
       m_resyncPending = true
       sendGetSnapshot("resync")
   DO NOT return
6. apply the full snapshot immediately
7. any later stale resync response only clears pending and is ignored by
   nextRevision <= m_revision
~~~

Delete this blocking rule:

~~~text
if (m_resyncPending && requestId != "resync") return;
~~~

The boolean now means only "one resync probe is outstanding", not "freeze the
stream".

Connection loss still clears the entire authoritative state through the
existing disconnect path.

## 6.4 Deterministic tests

Extend `IpcFixture` with a held-resync mode:

~~~text
setHoldResync(true)
hasPendingResync()
releaseStaleResync()
~~~

When it receives request id `resync`, store the response instead of sending
it until released.

Tests:

~~~text
revision 1
stream full snapshot revision 3 -> apply 3 immediately + send one resync
stream revision 4 while resync held -> apply 4
release stale resync revision 1 -> stay revision 4

two additional gaps while resync held -> only one resync request
disconnect while resync held -> reconnect requires new handshake/snapshot
~~~

Do not "fix" this by adding longer QTRY timeouts.

After AUD5 require the full Desktop workflow green on Windows, Ubuntu and macOS,
plus the pinned 6.8.3 golden jobs.
